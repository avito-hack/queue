# Queue
Репозиторий представляет собой реализацию очереди пользователей на лимитированные товары для хакатона Авито "Лаборатория Кода".

# User story решения
Пользователь заходит на страницу лимитированного товара, как пользователь я хочу видеть:
- Количество товара
- Если товар в наличии
- - Количество человек, желающих купить товар (количество человек в очереди)
- - Кнопочку “Забронировать”
- - - Кнопка ставит пользователя в очередь
- - - - Очередь типа FIFO
- - - - Очередь отдельная на каждый тип товара (комбинация размера, цвета и т.д.)
- - - - Пользователь может встать только в ОДНУ очередь на одном товаре
- - - - Пользователь может встать в несколько очередей (разные товары)
- - - - Позиция пользователя определяется временем создания заявки на сервере
- - - - Пользователь может выйти из очереди с предупреждением по кнопке, после этого он может повторно встать только в конец очереди
- - - Прохождение очереди дает человеку тикет на покупку товара
- - - - Только тогда, когда пользователь использовал/лишился тикета, он может снова войти в очередь
- - - - Тикет не изменяет физический остаток товара, но закрепляет одну свободную единицу за пользователем и уменьшает количество прав, которые система может выдать.
- - - - Количество доступных тикетов = свободный остаток товара - тикеты - резерв товаров.
- - - - Тикет имеет таймер после которого он истекает
- - - - Тикет можно активировать - активация тикета перекидывает пользователя на страницу создания заказа с uuid тикета в аргументе ссылки, подтверждающим право на покупку товара (ссылка может открыться только при валидации тикета на id пользователя) и переходит на стадию погашения (погашается при успешной оплате)
- - - - Активация тикета активирует стандартный флоу резервирования товара на обычных объявлениях (со всеми ошибками оплаты и т.д.), который уже есть в авито
- - - - Таймер тикета ограничивает только время на его активацию. После успешной активации действуют сроки стандартного резервирования и оформления заказа.
- - - - При покупке товара, тикет сгорает
- - - - Наличие товара определяется только покупкой и резервацией, сами тикеты на это не влияют
- - - - Только 1 тикет = 1 товар на одного человека (за один проход по очереди), после покупки товара пользователь может снова встать в очередь
- - - - Каждому активному тикету соответствует одна единица товара, на которую система не может выдать другой тикет. Действующий тикет гарантирует возможность перейти к стандартному резервированию.
- - - - От тикета можно отказаться
- - - - Все пользователи стоят в очереди, пока товар физически не закончится
- - - Покупка товара осуществляется только через взаимодействие с тикетом на странице товара или со страницы со всеми очередями
- - - btw Можно не дергать очередь лишний раз, когда желающих мало, а выдавать тикет сразу
- - - При постановке в очередь появляется всплывающее окошко с переходом на понятный экран ожидания (на него так же можно перейти через “Мои очереди”)
- - - - Экран ожидания состоит из плиточек
- - - - Плиточка олицетворяет очередь со статусом в ней (товар/место и т.д.)
- - - - По плиточке можно перейти на страницу товара
- - - - По плиточке можно перейти на страницу оформления заказа
- - - - По плиточке можно выйти из очереди
- - - - По плиточке можно отказаться от тикета

- Если товар закончился
- - Если пользователь был в очереди
- - - Всплывающее окно “Упс, товар закончился”
- - - - Кнопка уведомить о поступлении в окне
- - - - Посмотреть аналогичные товары (уже есть внизу страницы с товаром)
- - - Кнопка уведомить о поступлении на странице товара

Продавец заранее включает возможность очереди для товара. Когда очередь активна, нажатие кнопки покупки всегда проходит через механику получения права на покупку. Если свободная единица есть и перед пользователем никого нет, право выдается сразу.

Пользователь может находиться в состояниях: неактивен/в очереди/
Защита от прямого вызова API: каждый запрос совершается с авторизационным токеном, который конвертируется в user_id. Если злоумышленник получит авторизационный токен, то он сможет совершать все действия, доступные пользователю.

# Микросервисная архитектура решения

Решение состоит из 5 сервисов (4 бэкенд и 1 фронтенд):
- Frontend (services/frontend) - отвечает за фронтенд
- Queue service (services/queue) - отвечает за всю логику с очередью
- Tickets service (services/tickets) - отвечает за всю логику с тикетами
- Avito adapter (services/avito-adapter) - отвечает за мок готового функционала Авито, предоставленного кейсом
- nginx - прокси на бэкенд для фронтенда

Коммуникация между сервисами осуществляется через REST API и RabbitMQ.

# Архитектура репозитория
## Глобальная архитектура
services/ - директория со всеми микросервисами
services/frontend - сервис фронтенда
services/queue - сервис очереди
services/tickets - сервис билетов
services/avito-adapter - адаптер Авито

schemas/ - директория с клиентскими схемами сервисов
каждая директория в schemas соответствует openapi схеме соответствующего сервиса в services/

## Типовая архитектура бэкенд микросервиса
api/openapi.yaml - серверная yaml документация openapi (копируется в schemas 1 в 1)

cmd/app/main.go - мейн, точка входа

config/config.go - чтение конфигов env/yaml

gen/ - сгенерированные openapi бойлерплейты на go
gen/server/ - сгенерированный сервер текущего микросервиса
gen/clients/ - сгенерированные клиенты внешних микросервисов из schemas/

internal/ - приватный код микросервиса, недоступен для импорта извне
internal/domain - чистая бизнес логика микросервиса, без привязки к инфраструктуре
internal/usecase - сценарии использования, каждой ручке соответствует отдельный usecase

infrastructure/ - инфраструктура/базы данных
infrastructure/repository - репозитории для чтения данных из бд
infrastucture/transport/http - REST API Gin, связка с роутером кодогенеренного сервера

tests/ - тесты testcontainers

build/Dockerfile - докерфайл для сборки сервиса
go.mod
go.sum

# Best practices
- Код пишется без комментариев (вообще)
- Тесты используют идиоматичное именование Golang
- Тесты пишутся с помощью фреймворка testify
- Тесты пишутся с комментариями по шагам given, when, then
Например:
```go
func Test_Add_ReturnSum(t *testing.T) {
    // given
    x := 5
    y := 2

    // when
    res := Add(x, y)

    // then
    assert.Equal(t, 7, res)
}
```
Либо с объединением шагов
```go
func Test_Something_ReturnSomething(t *testing.T) {
    // given
    x := 5
    y := 2

    // when / then
    ...
}
```
- Сервисы генерят себе клиентов из schemas/ через oapi-codegen
- Сервисы генерят Strict Server для роутера Gin через oapi-codegen
- Сервисы используют валидаторы REST запросов через oapi-codegen middleware
- Ошибки не глушаться, а хэндлятся
- Сервисы поддерживают healthcheck и graceful shutdown
